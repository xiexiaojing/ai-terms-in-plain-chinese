依赖只有 numpy 和 httpx，本机不跑模型、不下权重。用哪家模型都行——OpenAI、通义、智谱、硅基流动、本地 Ollama，改 .env 里三行就能换，向量化那边 OpenAI 兼容协议和 MiniMax 私有协议都认。没配 key 也能开，检索会退成纯字面匹配。先搜几个问题玩十分钟再听课——手上有感觉，后面每一站你才知道我在说哪儿。

文章进来：决定什么算语料

8 分钟 · scripts/ingest.py

660 篇文章和漫画进索引之前，先要回答一个不技术的问题：哪些算数。这套系统的答案是「已发布的才算」，判据是有没有公众号链接。没链接的一律不进，包括写完没发的存稿。

这条规矩把 34 篇挡在外面。听起来只是个过滤条件，但它决定了系统会不会说谎：一个没发表过的观点，被检索出来当成「我写过」，比检索不到糟糕得多。

翻车现场 · 内部内容漏出去

第一版索引建完，随手点开一篇的「展开全文」，冒出来这么一行：

> 2026-08-17 增长改版：原标题是索取姿态 + 格言体，
> 已发布版本保留备查。本次只动引导语，正文不动。

这是写稿时给自己留的编辑说明，读者从来没见过。同一批还有「发文前需人工确认的事实点」19 篇、「作者置顶评论（自己先抛，引互动）」19 篇、灌稿命令和后台文章 id。

清洗按小节层级做，不能逐行判。逐行判会把说明段切碎，留下半句「原标题是索取姿态」这种更难看的残渣。丢一个小节就丢到下一个同级标题为止。

切块这里有个容易含糊过去的选择：按固定字数切，还是按小标题切。这套按小标题切，平均 357 字一块。一个小节通常就是一个完整意思，定长切法会把一句话劈成两半，两边都答不了问题。

向量化：本机跑还是调接口

10 分钟 · scripts/embedding.py

3968 块要变成向量。第一版用本机模型 bge-base-zh-v1.5，768 维，Mac 上 48 秒跑完，不联网不花钱，听起来哪儿都好。

翻车现场 · 你们装不上

本机跑模型要 pip install torch，2GB；模型权重另外 391MB。我这儿早装好了所以没感觉，直到要把包发给你们。网速好也得十几分钟。「课前几分钟搭好」当场变成空话。

换成调接口后依赖只剩 numpy 和 httpx，pip 装完 31 秒，全库 3968 块编码 91 秒。今天演示用的是 MiniMax 的 embo-01，换成别家只改 .env，代码一行不动。

教训在别处：「在我机器上能跑」和「别人能装上」是两件事，后者往往才是技术选型里真卡人的那一条。

torch 是跑神经网络的运行时，不是可选的加速库。bge 是 BERT 结构，把一句话变成 768 个数要过 12 层 Transformer，几千万次矩阵运算，这些算子得有人实现。2GB 是因为它把 CPU 版、CUDA 版、MPS 版的内核全预编译进去了，你只用得上一份。

换接口之后，那几千万次运算发生在人家机器上，本机收到的是算好的 1536 个数，剩下只有一次点积，numpy 就够。本机跑模型和调接口的真正分界，在于前向计算发生在谁的机器上，跟联不联网没关系。

换向量模型必须重建索引（./refresh.sh）：维度和向量空间都变了，不重建的话查询跟库里的向量根本不在一个空间，检索会安静地全乱、不报错。服务启动时会核对索引里记的模型，对不上直接在日志里说。

还有个坑：MiniMax 的 embedding 是非对称的，入库传 type=db，查询传 type=query，混用会掉精度。bge 则要求查询侧加固定前缀。这类要求写在各家文档里，不看就白跑一遍。

两路检索：语义一路，字面一路

我扫了 30 个查询，纯向量在 7 个上选错了第一名，全是这两类：一词多义（token、缓存、锁）和专有名词（人名、书名、缩写）。而这 7 个的分数跟混合检索只差 ±0.1——光看分数根本看不出问题，得看排序。

翻车现场 · 我差点删掉 BM25

换成 MiniMax 之后我一度想删掉字面这一路：分数差距那么小，四十行代码不如省了。

幸好先扫了一遍排序，才看见那 7 个跑偏的第一名。如果只盯着分数做决策，这一路就删了，然后在某个学员搜「省 token」的时候安静地给出一篇讲 JWT 的文章。

字面这一路是自己写的 BM25，k1=1.5、b=0.75，中文按 2-gram 切词省掉分词器依赖。还有个细节：建 BM25 索引时把标题并进了每一块，否则「杀猪盘」这种只出现在标题里的词，正文一次都不出现，字面路也命中不了。

融合：两个分数怎么合成一个

12 分钟

加权和，语义 0.72、字面 0.28。合之前要把 BM25 归一化——它没有上界，跟余弦不在一个量级。第一版写的是「除以本次查询的最大值」，看着很自然。

.venv/bin/python scripts/demo.py 归一化 "钢琴考级怎么准备"
BM25 归一化方式          分数 判定      第一篇
────────────────────────────────────────────────────────
饱和 lex/(lex+12)  现在  0.27 没写过   《意识型面试题：我们更换了证书…》
除以本次最大值    旧写法    0.42 擦边    《朋友两年没上班，在准备移民德国》
她没写过钢琴考级。旧写法把分数抬到 0.42，结论从「没写过」变成「擦边」，系统开始暗示一篇根本不相干的文章。
.venv/bin/python scripts/demo.py 归一化 "怎么挑西瓜"
饱和 lex/(lex+12)  现在  0.23 没写过   《CURD系统怎么做出技术含量…》
除以本次最大值    旧写法    0.32 擦边    《白话 TCP/IP 原理》
同一个毛病。「除以本次最大值」意味着每次搜索都必然有一块拿到接近满分，哪怕全库没有相关内容，分母是本次查询自己的最高分。

改成饱和归一化 lex / (lex + 12)，分数才有绝对含义：命中得多、命中的词罕见，分才高。这个问题根源藏得很深，因为它不影响排序，只影响分数的量级——而「写过没写过」这个判断，恰恰只看量级。

另外两个文档级加分项：一篇里多处命中，每处 +0.035（封顶 3 处）；查询词跟标题重叠，按比例最多 +0.18。块级分数聚合到文章时取最高块，不求和——求和会让长文虚高：一篇一万字的文章顺带提八次，加起来能压过专门写它的短文。

片段：给人看的那几行

5 分钟

检索到的是块，呈现给人的得是「能读懂的一段」。三个细节决定它像不像人做的。

截取从命中词附近开始，然后往前找最近的句号，避免从半句话中间起。markdown 记号在展示前抹掉，正文里的互链只留标题不留网址。高亮要过滤停用词——两个字都是虚词的 2-gram 全高亮，满屏是黄的。

这一站没有翻车故事，但它是做完 demo 之后最容易被夸的地方。检索质量看不见，片段读着顺不顺，一眼就看得出来。

判断：这个观点到底写过没有

25 分钟 · 全课的重点

前面五站都在排序。但这套系统真正要回答的是个是非题：这个观点我以前写过吗。排第一的那篇分数 0.9，到底算写过还是没写过？

方法是准备两组问题，各自去搜，看两组分数区间隔不隔得开。中间那段空隙就是分离度——它是留给阈值的空间，空间越大这条线越不容易划错。

.venv/bin/python scripts/demo.py 分离度
【确定写过】10 个
  检索分数  0.89 ~ 1.14      标题匹配  0.85 ~ 1.00
  判定分布  写过×10

【完全没写过】5 个
  检索分数  0.23 ~ 0.29      标题匹配  0.03 ~ 0.25
  判定分布  没写过×5

【难负例·沾边但没专门写】3 个
  检索分数  0.86 ~ 0.99      标题匹配  0.24 ~ 0.67
  判定分布  擦边×3
看第三组。它的检索分数 0.86~0.99，跟「确定写过」那组完全重叠——光靠分数，这三个必然被判成「写过」。救回来的是标题匹配那一列。
翻车现场 · 我的评估集里没有难题

标定阈值时我用的负例是羽绒服、猫藓、插花、螺蛳粉——跟她的领域八竿子打不着。这种负例谁都能分对。

后来补了三个难负例：Redis 缓存穿透、MySQL 索引失效、线程死锁。都在她的技术领域内，她也确实在《面试题总结》里顺带提过一两句，但没有一篇专门写。这才是真实使用中最常问、也最容易判错的那一类。

用难负例一测，原来那套判错 3 个。分离度 +0.034 的方案，实际判错率是 +0.002 那个方案的三倍。不是指标错了，是我喂给指标的测试集里没有难题。

诊断了三条路：向量分（难负例 0.93~0.95，跟正例 0.96~0.99 贴着，救不了）、块分数分布（婆媳 0.81 = Redis 缓存穿透 0.81，分不开）、命中块数（Redis 缓存穿透在《面试题总结》里命中 19 块，反而最多）。只有标题分得开。

.venv/bin/python scripts/demo.py 判定 "Redis 缓存穿透"
  第一名        《面试题总结》
  检索分数      0.99   ≥ 0.60 ✓
  标题匹配      0.24   < 0.70 ✗ 没有一篇标题在讲这个
  命中块数      19

  结论          擦边
  （只看分数不看标题的话会判成「写过」——标题这一条就是拦这个的）
《面试题总结》是个大杂烩，什么都提一句，所以命中 19 块、分数 0.99。但标题跟问题毫无关系。「专门写过」和「顺带提过一句」的区别，就藏在标题里。

标题匹配取两个信号的最大值，因为两条各有各的盲区：

查询库里的标题字面重叠标题语义取大
婆媳关系怎么处我的婆媳相处之道0.170.950.95
熔断的原理稳定性五件套-熔断的原理和实现1.000.341.00
Redis 缓存穿透面试题总结0.000.240.24

「熔断的原理」的标题语义只有 0.34，是被系列前缀「稳定性五件套-」稀释的。编码标题前把这类前缀剥掉，它就升到 1.00 了。

最后「写过」这个结论要两个条件同时成立：分数 ≥ 0.60，且标题匹配 ≥ 0.70。标题不混进分数，单独当一道闸：分数管「相关不相关」，标题管「有没有一篇专门写它」。

判错 0/21
21 个没参与过阈值标定的新问题，真值用全文精确匹配定的，不靠检索系统自己判——那是循环论证。加上原来的 32 个，两个集合共 53 个查询，硬错 0。

课堂提问：分离度高，是不是就说明检索做得好？
不是。分离度只管「有没有」这个是非题，不管「哪篇最相关」。第三站那些跑偏的第一名，分数一个都没异常。两件事要分开测，别用一个指标糊弄自己。

生成：让它用我的话回答，还得说出处

10 分钟 · scripts/answer.py

到这一步才轮到大模型出场。前面六站做的事，就是给它一份「只包含我说过的话」的材料。提示词里最重要的一条：片段里没有的一个字都别加，包括你自己知道的正确答案。

curl -sN "localhost:7788/api/ask?q=怎么挑选羽绒服"
  事件 sources     首条 0.29
  事件 no_answer   ← 根本没调模型
检索最高分低于 0.30 时连模型都不调，直接回「这个我没正面写过」。省钱是次要的，主要是断掉硬编的机会。材料不够时，模型会把缺口自己填上。
翻车现场 · 角标全丢了

提示词里明明白白要求「每段末尾标 [编号]」，读者要靠它点回原文核对。实测三次里有一次一个角标都不带，答案照样写得很漂亮。

把要求从 system 挪到 user 消息末尾（紧挨生成位置），稳定了一些，但没有全好。

调提示词到此为止，解法挪到前端兜底——不管模型带不带角标，答案下方固定列出这次用到的文章，带链接。可溯源是 RAG 的命门，不能指望模型自觉。

这就是 RAG 里 G 那一步的真相：模型负责组织语言，事实和出处由工程保证。你在提示词里写多少遍「不要编造」，都不如让它根本拿不到可编造的材料。

要不要上编排框架

7 分钟

课上一定有人问 LangGraph。先看这套系统跑一次搜索的形状：编码查询 → 两路检索 → 融合 → 聚合 → 判定 →（分够高才）生成。一条直线，没有分支、循环、跨步骤状态，也没有中断恢复。全部逻辑 400 行 Python。

LangGraph 解决的是有向图里的编排问题——ReAct 循环、多 agent 协作、条件跳转、检查点续跑、人工介入节点。这套一条都不占。硬套上去，依赖从 2 个变十几个，27 秒的安装泡汤，400 行直白代码变成节点定义加状态类型加图编译，学员得先学框架才读得懂检索逻辑。

什么时候真有意义：检索分低时让模型改写问题再搜一遍（真循环，还得设退出条件）、多轮澄清、检索和生成之间插人工审核。到那一步框架给的是可观测性和状态持久化，在此之前一个 while 加几个 if 更清楚。

顺带说一个融合方式的对照。不少工单诊断类系统用 RRF 倒数排名融合（score = Σ 1/(k + rank)），好处是根本不用管两路分数的量纲，省掉归一化那一整块麻烦。代价是它输出的分数只有相对含义——第 1 名比第 2 名高多少，跟「这件事到底处理过没有」没关系。第四站那个问题根源，RRF 是结构性地一直有。

今天带走这六条

01RAG 的功夫八成在 G 之前。调模型是最后十分钟的事，前面七站决定了它手上有什么材料。
02光看分数会漏掉排序问题。纯向量在 7 个查询上选错第一名，分数只差 ±0.1。一词多义和专有名词是它的固定盲区。
03分数要有绝对含义。「除以本次最大值」这类相对归一化，会让没写过的话题也拿到高分，阈值就此失效。
04评估集里必须有难负例。领域内、沾过边、模型最容易混的那些。全是远距离负例的评估，分数好看但跟真实使用没关系。
05是非题需要第二个信号。「相关」和「专门写过」是两回事，分数管前者，标题管后者。一个信号扛不住两个问题。
06可溯源靠工程，不靠模型自觉。模型会漏角标、会补全、会自信地编。兜底代码写在它够不着的地方。
