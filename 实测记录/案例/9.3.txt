书稿案例摘录（不是原始请求日志）
来源：v3/第9章-算清成本.md
整理日期：2026-10-02

按用量计费是通用的收费方式。文本模型 API 常按输入、输出和缓存 token 分项计价；图片、语音、工具调用等可能另按其他单位收费，聊天产品也可能按套餐提供额度。先查使用的产品与接口怎样计费，再核对实际用量；已计费用不会因答案无用而自动退回。

这跟多数按次、按月收费的服务不一样，得先习惯。下面是我当时抄录的一份中文价目表，该平台也提供免费模型；这里讨论表中这一型号的输入、输出与缓存价格：

| 上下文 | 输入单价 | 输出单价 | 缓存命中 | 缓存存储 | 输入模态 |
| --- | --- | --- | --- | --- | --- |
| 1M | **8 元／M** | **28 元／M** | **2 元／M** | 限时免费 | 文本 |

单价的单位都是元每百万 token（M 就是百万）。

聊天套餐的额度可能按消息、任务或其他用量规则限制，不一定公开 token 配额。看账号的用量说明，不能照搬 API 的单价计算订阅额度。

### 比较价格，要分别计算输入、输出与缓存

在这张价目表中，输出单价是输入的 **3.5 倍**，缓存命中是普通输入的 **四分之一**。这比较的是每个 token 的价格，不能直接换算成每个汉字的价差。重复内容也只有符合平台缓存条件并实际命中时，才能按缓存价计算。

### 输入输出单价，要查平台计费规则

许多文本模型可并行处理输入，生成时则逐个产生 token，通常需要不同的计算资源。但价格还取决于模型与服务策略，不能把“500 个字”直接等同于“500 轮计算”。

> **作者亲历**：不加机器人标识，是因为当年那个价钱撑不起闲聊
>
> 我们的客服问答机器人刚上线时，用户看不出回话的是机器人还是真人。这是在标识规定出来之前，后来我们按规定加上了标识。
>
> 我翻当年的记录，发现产品当时担心：用户一旦知道对面是免费机器人，就会大量问天气、笑话等无关问题。每句闲聊都要调用模型，既带回复的用量，也带客服规则的输入成本。那时的价格下，团队试图靠不亮标识减少闲聊。
>
> 这又带来另一项要求：用户把答复当真人的话，答错一句也会算在我们头上。团队因此增加判断，表达情绪或发来识别不可靠的图片、视频时，默认不回复。省了部分模型调用，却增加了判断规则、人力维护和该答未答的代价。
>
>
> 后来模型成本降低，我重新提出加机器人标识：当年的价格前提已经变化，由此增加的判断和维护工作却仍在。现在已经按规定亮出标识。回看这件事，我要求把省钱办法的前提和日期记下来，价格变化后重新算账；标识要求则要按规定落实。

**基础练习**：可以记录任务、来回轮数、可见输入输出长度，比较工作过程；这些不是实际 token 或费用。模型没有账单读取权限时，它自己报出的用量也不能当作账单。

我向能读取实际用量记录的工具提出过下面的要求：


```text
把刚才这件活用了多少 token 进去、多少出来、多少钱，列给我。
```

看不到账单时，可先读下面的实测表，区分新写的文字、实际输入量与费用；字数不能代替用量。我的测试任务是“加一个字数标签”：

| 项 | 数 | 说明 |
| --- | --- | --- |
| 我打的字 | 47 个 | 那一句“加一个字数标签……” |
| 送进去的 token（含重发） | 845,333 | 23 圈，每圈把前面全部再送一遍 |
| 其中按缓存价读的 | 817,580 | 占 97% |
| 它写出来的 token | 5,634 | 代码改动＋汇报 |
| 费用 | $0.434 | 按 token 算，不按“我问了一句”算 |

我打了 47 个字，送进去的是 84 万个 token，它写出来的 5634 个。账单上没有“问了几句”这一栏，它按输入和输出的 token 数计费，其中 97% 的输入是每轮重复提供的内容。

> 实测记录：（任务与轮数 / 可见输入输出长度 / 实际用量和费用或未知项）
