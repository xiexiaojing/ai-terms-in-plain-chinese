批处理（batch processing）说的是这种做法：攒一批一起交，不一条一条等着回。按这个做法开出来的接口，OpenAI 叫 Batch API，Anthropic 叫 Message Batches API，国内平台上也常写作批量推理。把一批请求打包交上去，平台异步处理。以 OpenAI 和 Anthropic 的这两种接口为例，文档给出的处理窗口是 24 小时，标准批处理用量价格比实时接口低 50%；具体模型支持、限制和价格，以所用平台的现行文档为准。2024 年 OpenAI 先推出，Anthropic 同年跟上。

不需要即时结果的任务，可先比较批处理的价格与完成时限；有折扣且时限合适时再采用（图 10-3）。


它不保证在你期望的某个时刻完成，因此不适合需要即时返回的在线业务。赶明天早上的交付，也要先确认剩余时间覆盖平台的完成窗口，并给失败重试留出余量。

### 采用批处理，要确认容量与截止时间

批处理接口一次最多收多少条，量大的活装不装得进一批；最晚什么时候必须交，排队超过这个点，省下的钱抵不抵得过误了事的损失。

### 合并提问与批处理，要分开算收益

我比较过“一题一问”与“多题合问”，结果如下；这些数据不能用来推定 Batch API 的折扣。

**基础练习**：可以把 20 道题分组提问，比较组织方式、耗时和正确率；这不属于异步批处理接口，也不享有该接口的折扣。


|  | 分 20 次 | 拼成一条一次问 |
| --- | --- | --- |
| 进去的 token 合计 | 10,617 | 1,187 |
| 写出来的 token | 3,149 | 1,321 |
| 一共等了 | 52 秒 | 15 秒 |

这 20 道题问的是同一份制度。分 20 次问，检索出来的那几段和那段规矩，每一次都得重新发一遍，一共发 20 遍。

拼成一条一次问，制度只发 1 遍，后面跟着 20 道题。**进去的量少了九成。**

合并提问改变的是输入组织，Batch API 改变的是请求提交与处理方式，两种办法的节省应分别核算。合并后的请求也可以在支持它的批处理接口中提交，仍需检查单条限制、质量与完成时限。

**思考**：即时问答和隔天交付的报表，哪一种适合批处理？选择时要核对哪些条件？

**参考答案**：隔天交付的报表更适合。先核对完成时限、支持模型、请求限制和价格；需要即时回复的任务不应仅为折扣改用批处理。
