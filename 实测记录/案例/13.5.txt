书稿案例摘录（不是原始请求日志）
来源：v3/第13章-分头办事.md
整理日期：2026-10-02

子 Agent 描述的是任务分派中的角色关系；各产品怎样创建、共享资料和返回结果，需分别确认。

主 Agent 要写一份报告，得先查五份资料。它可以自己一份份查，五份全堆进它的上下文，报告还没开始写，窗口已经满了。派五个子 Agent 去查，每个只带回一段三百字的摘要，主 Agent 的上下文就干净了。

子 Agent 的一个重要作用，是减少主 Agent 需要读取的中间过程。资料量大、处理过程长、但最终结论短的任务，适合由子 Agent 处理后汇总。

### 子 Agent 交回摘要，主 Agent 未必看见原文

它带不回它没被问到的东西。子 Agent 只交回它认为该交的那一段，主 Agent 看不到原文。

漏的东西重要不重要，看它是不是撑着结论的那一块。核它交回来的摘要，先找撑结论的那几句，再回原文看那几句有没有被改过。

派出去也要花钱，花在开场白上。每个子 Agent 开工前都得先被介绍一遍：常驻位、项目背景，加上它自己去“熟悉一下情况”读的那几个文件。

派十个，这份介绍就付十遍，我管这笔叫**介绍费**。判的时候数一数：这十份上下文里，同一份内容重复了多少。

重复得多就该合并，或者把共用的那部分先算一次，再把结果分发下去。多个请求同时开始时，尚未写完的缓存不能供其他请求读取，可能各自重复处理材料。已有缓存能否复用，还要看平台、模型和请求前缀；重复传入十份材料，不等于十次费用一定相同。


**作者亲历**：十个自查全报“没问题”，一个质检抓出 22 张

做一套 97 集短片时，我派十个 Agent 分头出图，并要求各自检查。十个回来，都报“没问题”。我打开图才发现，有的人头和身子分开，中间空一截；有的手臂末端没有手（图 13-7）。

我另外派一个只看图、不再画图的 Agent 复查。同一张图，它标为重画；一张张看完，共标出 22 张需要重画。


回看任务要求，我发现标准里没有明确写“头要连着身子、手臂末端要有手”。这能解释我们漏掉了什么检查项，却不能仅凭这次结果确定各 Agent 为什么都报通过。

我随后把制作与验收分开：制作方交图，质检方拿到图和明确的标准，单独判断。质检只需本次验收的材料，不必重读整套制作上下文。标出的缺陷仍要核实；独立验收增加了一道检查，不等于换一个 Agent 就一定正确。

**基础练习**：把任务拆成两份交接单，分别说明材料、职责和交付物；这不能证明工具实际创建了子 Agent。


|  | 主 Agent | 子 Agent 甲 | 子 Agent 乙 |
| --- | --- | --- | --- |
| 开工前先读的 | 工具说明、规则、目录 | 同一份，再读一遍 | 同一份，再读一遍 |
| 干的活 | 派人、等、汇总 | 读 server.py 找冒号 | 读 index.html 找冒号 |
| 交回来的 | 一张表 | 一段话：2 处，在哪几行 | 一段话：列了 8 处，说是 7 处 |

主 Agent 和甲、乙两个子 Agent，开工前读的是同一套东西，介绍费付了三份，三份一模一样。乙交回来的摘要自相矛盾：列了 8 条明细，却说是 7 处。主 Agent 看得见的只有这段话，看不见它到底读了什么，是靠这 8 条明细才发现“7 处”数错了；要是它只交一个数，谁也纠不了。
