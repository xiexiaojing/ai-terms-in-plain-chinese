# 一份规格：一条把文章改成漫画的产线

《用人话讲 AI 名词》配套资源，配第 4 章“改稿”和第 2 章“质检”读。

---

## 它为什么改了形状

这不是编出来给书当例子的。它是我自己那条漫画产线在用的东西，改过几十版，每隔一阵
就因为出了丑图返一次工，回来改一条。带日期的那些行，每一行背后都是一批废图。

原来它是一段提示词。这一版我把它改写成了规格，动的地方只有一处：**加了验收。**

一段提示词和一份规格差三条：约束写在哪儿、改需求怎么改、怎么知道做对了。
第三条是分水岭：**提示词写完靠人感觉；能拿它判定实现对不对，才算规格。**
前两条我早就做到了，这本来就是个独立文件、进了版本库、改需求就改这一份。
第三条一直缺着，缺的那阵我判图全靠眼睛，一张一张看，还看漏过。

所以这一版的顺序反了过来：前面四节是规格，最后一节才是我在用的那段提示词——
**它是实现，不是规格。** 你可以写一段跟我完全不一样的提示词，甚至换一个工具，
只要过得了第四节那张单子。

---

## 一、意图

把一篇写好的文章，改成一组“简短格文案 + 漫画配图”的图文，全部文案做进配图里，
正文一个字都不放。

它要解决的是同一个角色在十二张图里长成十二张脸，以及不该出现的东西被画进去。

---

## 二、要先定死的项

下面这些，我这边每一项都有固定答案，写在提示词里一个字都不许改。
你的答案跟我的不一样，但**该定的项是同一批**——定不下来，同一个角色出十二张能有十二张脸。

| 要定的项 | 我这边的做法 | 为什么必须定死 |
|---------|------------|--------------|
| 主角称呼 | 全篇统一一个称呼，旁白、格文案、画图提示词都用它 | 换称呼模型会当成换人 |
| 主角性别与视角 | 明确写死，包括技术类内容的解说员 | 不写，默认多半给你男的 |
| 年龄怎么描述 | **只写气质，绝不写岁数** | 见下面“教训四” |
| 配角形象 | 一两条硬特征（发型、戴不戴眼镜） | 特征越少越稳，越多越容易前后打架 |
| 出镜的品牌 / 账号名 | 名字 + 头像文件固定 | 界面类画面里最容易画歪的就是这个 |
| 基准锚图 | 一张定稿的人物图，每次出图都作为参考图带上 | 见“教训三” |
| 不公开的信息 | 明确列出来，写进提示词当禁令 | 模型不会自己知道哪些不能画 |

最后一行值得多说一句。我这份提示词里有一条是“某人姓名不公开，画面文字、标签、格文案说明里
一律不许出现”。这条跟画风没关系，它把一条隐私约束写成了硬约束。跟第 7 章一个道理，
写在脑子里的规矩，系统读不到。

---

## 三、硬约束：六条踩出来的教训

**教训一：形容词会跟参考图抢权重，而且形容词往往赢。**
给了基准锚图之后就别再堆风格形容词。实测过一次（2026 年 8 月）：砍掉十几行形容词、只留“照抄基准图”，
一次就对了。之前那十几行每一行都是“为了画得更准”加的，合起来把锚图挤没了。

**教训二：画面栏只写“必须有什么”，别写“该怎么拍”。**
构图、姿势、镜头、配色一律不写死。约束加得越多，工具发挥空间越小，人物越画越僵。
小瑕疵如果只能靠加一堆约束才修得掉，那就别修——好看比规整重要。

**教训三：每张图都带上同一张基准锚图。**
这条后来直接写死进了出图脚本，不靠人记得。凡是“靠人每次记得加”的约束，
迟早有一次忘了，而那一次的图你未必当场看得出来问题。

**教训四：别写实岁数。**
写“30+”“middle-aged”“三十多岁亚洲女性”这类词，模型会照着真实的中年人画，
一点美化都不做。写气质、写打光、写神采，不写数字。这条是被读者当面指出来才改的。

**教训五：负面提示词要往两个方向同时禁。**
只禁一头，它就滑到另一头去。想要日系动漫风，就得同时禁掉水彩绘本那一端
（`watercolor picture-book, lineless, realistic small eyes`）
和漫画那一端（`heavy bold black outlines, exaggerated manga eyes, comic panel look`）。
只写“不要水彩”，出来的就是浓黑边的漫画风。

**教训六：所有硬约束都标上立规矩的日期。**
这份文件里凡是“硬要求”都跟着一个日期。过半年回头看，你能分清哪条是当初拍脑袋定的、
哪条是出事之后补的。补出来的那些一个都不能删——它们看着像废话，是因为它们已经在生效了。

---

## 四、验收（做错了我能指出来）

生成式的输出没法靠“像不像”验收，所以这张单子只管能判红判绿的那一半。剩下那一半
（好不好看）留给人挑毛病——第 2 章那笔账算过，画一张的钱远不如挑毛病的钱贵。

**每一条都要能不看图就判，或者能交给另一个程序去判。**

1. **张数和字数**：10–12 张；每张文案 15–40 字，金句放宽到 60。超了算红。
2. **图内文字逐字一致**：格文案本来就是文本，成品图里的字必须跟它逐字对得上，
   含标点和数字。这一条人眼查太慢，交给一个专门查图的程序去查，它比我耐心。
3. **人物一致**：拿定稿的第一张当基准，后面每一张比三项硬特征——发型、戴不戴眼镜、
   服装主色。变了算红。
4. **禁列表为空**：不该出现的东西（真实姓名、公司名、标识、二维码、账号 ID）在成品图里
   一处都没有。**这一条最要紧，因为它错了收不回来。**
5. **每张图都带了基准锚图**：查脚本的调用记录，不查人的记忆。少带一张算红。
6. **命名和目录**：图按顺序命名、预览页在、目录结构对得上。
7. **提示词里没写岁数**：全篇搜“数字 + 岁 / 多岁 / middle-aged”，搜到算红（教训四）。
8. **两头都禁了**：负面提示词里两端的词都在（教训五）。只禁一头算红。

第 2 条和第 3 条自己就是一个程序。**给生成式产线做验收，验收本身通常也得是个程序**——
这就是第 2 章一整章在讲的事。

## 五、我这一版的实现（提示词原文）

下面是我实际在用的那段提示词，人物设定换成了占位符，方法和踩过的坑一条没删。

**它是实现，不是规格。** 放在这儿有两个用处：一是你可以直接抄走开工；二是看形状——
一份长期在跑的提示词最后会长成什么样。前面是流程，中间是硬约束，后面全是“不要怎么写”。
越靠后的条目越像禁令，而且大多不在告诉模型该画什么，全在拦着自己别多说话。
第 4 章讲的那件事，在这份文件里能直接看见。

### 5.1　一键生成

```
帮我画一个漫画公众号文章，所有文案都是配图形式，不要正文纯文字。

【标题】
【主角】（名字 + 人设）
【风格】（如：温暖日常 / 职场幽默 / 技术纪实 / 四格漫画）
【色调】（如：暖色扁平插画 / 蓝白科技风）

按时间线拆成 10–12 张图，每张图只放一段简短文案（15–40 字），金句可稍长。

时间线：
【07:30】……
【09:00】……
【12:00】……

要求：
1. 第 1 张是封面，大标题居中
2. 每张图内嵌中文文案，字体清晰可读
3. 主角形象前后一致
4. 可适当加内心 OS、对话气泡、梗图元素
5. 生成后整理到独立文件夹，含 index.html 预览页
6. 图片按顺序命名，方便直接上传
7. 美是第一要务：人物要好看、画面要舒服。上面这些是底线不是天花板，
   构图、光影、道具、镜头、情绪表达都放手发挥，别拘着。
   凡是“为了满足某条要求而把画面画僵、把人物画丑”的做法，一律反过来——先保证好看。
```

第 7 条是后来补的，补之前那阵出的图，每一张都严格满足了要求，每一张都难看。

---

### 5.2　长文改漫画（文字先行）

```
帮我把下面这篇文章改成“简短格文案 + 漫画配图”的形式。

规则：
- 原文保留核心情节和金句，每格压缩成一句口语化短文案
- 删掉冗余描写，保留：时间、动作、对话、内心 OS、技术梗
- 先输出格文案表（序号 | 时间 | 画面 | 文案），我确认后再出图
- 全部文案做进配图里，正文零文字
- 画面一栏只写“必须有什么”（人物、动作、关键道具、场景），
  不要把构图、姿势、镜头、配色写死——留给出图时自由发挥，画得好看最重要

【粘贴原文】
```

“先输出格文案表，我确认后再出图”这一句是花钱买来的。图是这条链路上最贵的一步，
让它先把十二格的文案列出来，错了改一行字，比出完十二张再返工便宜得多。
这就是第 5 章说的：把贵的那一步挪到后面，让便宜的那一步先拦一道。

---

### 5.3　单张配图的提示词结构

```
Chinese webcomic panel, flat illustration.
Character: 【主角外貌：性别、发型、服装、标志性道具】
Scene: 【画面描述：地点、动作、道具、表情】
Mood: 【情绪：轻松 / 紧张 / 幽默 / 温馨】
Chinese text overlay (must be legible): "【中文文案】"
Style: warm pastel colors, clean layout, no watermark.
```

封面额外加：

```
Cover panel. Large bold Chinese title at top: "【标题】".
Protagonist in hero pose, subtitle vibe matching article theme.
```

---

### 5.4　文案压缩原则

| 原文类型 | 漫画版写法 |
|---------|-----------|
| 长段叙述 | 一句时间 + 一句动作 |
| 用户反馈 | 对话气泡，保留原话感 |
| 内心戏 | “内心：……”或 OS 气泡 |
| 技术排查 | 关键词 + 结果（如：P95 48 秒 → 6 秒） |
| 会议 / 总结 | 清单式 |
| 金句收尾 | 单独一张结尾图 |

压缩前后长什么样：

- 原文：“上线后头一个小时监控一切正常，第二个小时开始零星报警，翻日志才发现缓存没预热，
  请求全打到库上去了。”
- 漫画：“10:00 一切正常。11:00 全线飘红——缓存忘了预热。”

### 5.5　目录结构

```
comic/
├── prompt.md          # 本提示词
├── assets/
│   ├── style-anchor.png   # 人物基准锚图
│   └── avatar.png         # 出镜账号头像
├── 制作中/【标题】/
│   ├── images/
│   ├── index.html
│   └── article.md
└── 已归档/【标题】/
```

新的建在 `制作中/`，发布后整夹移进 `已归档/`。预览页宽度按目标平台正文宽度设，
公众号是 677px。

---

**用法**：把【】换成你的内容，第二节那张表逐行填出自己的答案，然后拿第四节那张单子验收。
第三节不用改，它讲的不是漫画，是你跟任何一个生成式工具打交道时，话该说到哪儿为止。
